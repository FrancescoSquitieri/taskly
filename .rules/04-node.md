# Backend Rules — Node.js + Express (`apps/api`)

> Before reading this file, ensure you have read `02-servercn.md`. Many concerns here are implemented via servercn components.

## General philosophy

- Write **idiomatic TypeScript** — narrow, explicit, no magic.
- Prefer **simplicity and clarity** over abstraction. Do not introduce an abstraction until there are at least two concrete cases that need it.
- **No unnecessary interfaces** — only define an interface when there are multiple implementations or when testing requires it.
- **No global state.** Pass all dependencies explicitly via function parameters or struct fields (composition root pattern). The Express `app` is the only acceptable "global."
- **Composition over inheritance** for sharing behavior across domains.

## Architecture — feature-based

Per `servercn.config.json`, the project uses `architecture: "feature"`.

```
apps/api/src/
├── features/
│   ├── task/
│   │   ├── task.routes.ts        # Express routes — thin
│   │   ├── task.controller.ts    # Request/response shaping — thin
│   │   ├── task.service.ts       # Business logic
│   │   ├── task.repository.ts    # Data access (Prisma)
│   │   ├── task.types.ts         # Local types (most types are in @repo/types)
│   │   └── task.validation.ts    # Zod request schemas (uses @repo/schemas where possible)
│   ├── auth/
│   ├── tenant/
│   ├── project/
│   ├── user/
│   └── health/
├── middleware/                   # Cross-cutting middleware (auth, rate limit, error handler)
│   └── ...                       # Most generated by servercn
├── lib/                          # Infrastructure singletons (prisma client, redis client, bullmq, etc.)
├── jobs/                         # BullMQ queue definitions and workers (see 05-database.md)
│   ├── queues/
│   ├── workers/
│   └── index.ts                  # Worker bootstrap (run as separate process in prod)
├── realtime/                     # Outbound emitter that publishes to Redis (consumed by apps/ws)
├── config/                       # Env validation (servercn env-config component)
├── app.ts                        # Express app composition
└── server.ts                     # HTTP server + graceful shutdown bootstrap
```

**Realtime note:** `apps/api` does NOT host Socket.IO. Domain events are published to
Redis pub/sub via `realtime/emitter.ts` and consumed by `apps/ws` (see `06-realtime.md`).
`apps/api/src/realtime/` therefore contains only the publisher helpers, never `Server`
from `socket.io`.

- Group files by **domain**, not by layer. There is no top-level `controllers/` or `models/` folder.
- Each feature folder is self-contained.

## Layered responsibilities

Within a feature, layers have strict responsibilities. Do not cross them.

### Routes (`*.routes.ts`)
- Maps HTTP paths to controller handlers.
- Applies feature-specific middleware (auth, validation, rate limit).
- No logic.

### Controllers (`*.controller.ts`)
- Parse the request via the servercn Request Validator (Zod).
- Call the service.
- Format the response via the servercn Response Formatter.
- Wrap with the servercn Async Handler.
- **No business logic. No data access.**

### Services (`*.service.ts`)
- Contains all business logic.
- Calls the repository for data access.
- Calls other services if needed.
- Throws domain errors (via the servercn API Error class) on invalid states.
- **Never imports Prisma directly. Never imports Express types.**

### Repositories (`*.repository.ts`)
- The ONLY place Prisma is imported in feature code.
- Pure data access — no business rules, no validation.
- Returns plain domain objects. The service decides what to do with them.
- See `05-database.md` for repository patterns.

### Validation (`*.validation.ts`)
- Defines Zod schemas for incoming requests (body, params, query).
- **Whenever possible, compose from `@repo/schemas`** — do not redefine the entity shape.
  ```ts
  import { TaskSchema } from "@repo/schemas/task";

  export const CreateTaskBodySchema = TaskSchema.pick({ title: true, projectId: true });
  ```

## Error handling

- **Never ignore errors.** Always handle them, propagate them, or wrap them with context.
- Use the servercn API Error class for expected domain errors (validation failed, not found, forbidden, conflict). Throw them from services — the global error handler turns them into structured responses.
- Wrap async route handlers with the servercn Async Handler — never write `try/catch` in controllers just to forward to `next(err)`.
- For unexpected errors, let them bubble up to the Global Error Handler. Log them via the structured logger; the user-facing response stays generic.
- Never return raw error messages from infrastructure (Prisma, Redis, etc.) to the client.

## Authentication & multitenancy at the request level

- All authenticated endpoints sit behind the Auth Verification Middleware (servercn `verify-auth-middleware`).
- After auth middleware, the request has `req.user` populated with at minimum `{ userId, tenantId, roles }`.
- **Every database query in a service MUST scope by `tenantId`.** This is enforced via repository helpers (see `05-database.md` and `07-auth-security.md`). Forgetting this is a security incident.
- RBAC checks for permissioned actions go through the servercn RBAC component.

See `07-auth-security.md` for the full auth + multitenancy contract.

## Validation, end-to-end

1. The request hits the route.
2. The Request Validator middleware parses `body` / `params` / `query` against the Zod schema from `*.validation.ts`.
3. The controller receives a fully typed, validated payload.
4. The service trusts the input (types are guaranteed) and applies business rules.

**Never trust client input without Zod validation, even for "internal" endpoints.** There are no internal endpoints in a multitenant SaaS.

## Logger

- Use the structured logger from servercn (`add logger`). It exposes `logger.info`, `logger.warn`, `logger.error` with structured fields.
- Log levels:
  - `info`: request lifecycle, important business events (user signup, tenant created).
  - `warn`: recoverable issues (rate limit hit, retry triggered).
  - `error`: unhandled exceptions, infrastructure failures.
- **Never log secrets, tokens, full request bodies of auth endpoints, or PII** without redaction.
- **No `console.log`.** Anywhere. Ever.

## Naming (backend-specific)

In addition to the global naming rules in `01-project.md`:

- File naming inside `features/<domain>/` follows the pattern `<domain>.<layer>.ts` in kebab-case for the domain name (e.g. `task.service.ts`, `user-invitation.controller.ts`).
- Exported functions and types: PascalCase for types, camelCase for functions.
- Repository methods describe storage operations: `findById`, `findManyByTenant`, `create`, `update`, `softDelete`. Avoid HTTP verbs in repository methods.
- Service methods describe business operations: `createTask`, `assignTask`, `transitionTaskStatus`. Avoid Prisma verbs in service methods.

## TypeScript — backend specifics

- All exported functions, including all controllers and services, have explicit return types.
- Use `Request`, `Response`, `NextFunction` from `express` for handler signatures. Augment `Express.Request` once in `src/types/express.d.ts` to add `req.user`.
- Prefer `Prisma.TaskGetPayload<...>` and Prisma's generated types for ORM-level shapes. Convert to domain types (from `@repo/types`) at the repository boundary if the shapes diverge.

## Express setup essentials

The `app.ts` composition order matters:

1. Security headers (servercn `security-header`)
2. Body parsers, cookie parser
3. Request logger
4. Rate limiter (servercn `rate-limiter`, see `07-auth-security.md`)
5. Routes (each feature mounts its own router)
6. 404 handler (servercn `not-found-handler`)
7. Global error handler (servercn `global-error-handler`) — MUST be last

## Imports order

1. Node built-ins (`node:fs`, `node:path`)
2. External libraries (`express`, `zod`, `bullmq`, `ioredis`, etc.)
3. Internal monorepo packages (`@repo/schemas`, `@repo/types`, `@repo/constants`, `@repo/utils`)
4. Internal absolute imports (`@/middleware/...`, `@/lib/...`, `@/features/...`)
5. Relative imports
6. Types (`import type { ... }`)

Biome handles the sorting.

Already part of the stack (do not re-install if servercn brings them):

- `bullmq`

`socket.io` is NOT a backend (`apps/api`) dependency. It lives in `apps/ws` only — see
`06-realtime.md`.

**Path alias `@/*`** — both `apps/api` and `apps/ws` use a `tsconfig` `paths` mapping
`@/*: ./src/*`. Because the runtime is Node ESM (`module: NodeNext`), every alias import
MUST end with `.js`:

```ts
import { env } from '@/config/env.js';        // ✅ correct
import { env } from '@/config/env';           // ❌ won't resolve at runtime
```

The build pipeline is `tsc -p tsconfig.build.json && tsc-alias -p tsconfig.build.json`.
`tsc-alias` rewrites `@/foo.js` into a relative path in the emitted JS so Node can resolve
it without any custom loader.

Servercn-generated components may install additional dependencies. Let servercn manage
those installs.

**Anything not on this list or in a servercn component: ask before installing.**
